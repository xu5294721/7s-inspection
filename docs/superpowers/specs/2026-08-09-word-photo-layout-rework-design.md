# Word 检查项点照片排版重构设计

## 1. 目标

重构 7S 巡检 Word 报告中的照片排版，使检查项点文字与其全部照片保持视觉和分页上的一致性，解决以下问题：

- 单张照片占据过大区域，导致下一项点只剩文字在页尾；
- 照片为了适应页尾剩余空间被压得过小；
- 两个项点之间出现大面积、无计划的空白；
- 横屏和竖屏照片混排时，照片大小、行高和视觉重心不一致；
- 四张照片的表格在页间拆行，上一页显示上排、下一页显示下排。

本次只调整 DOCX 导出的排版算法，不改变检查流程、检查项点、照片分类、照片顺序、Word 正文内容和原始照片数据。

## 2. 当前问题的根因

当前实现把三个互相冲突的目标放在了同一套“自适应”逻辑中：

1. 按原始照片比例计算每张照片的高度；
2. 尽量利用当前页面剩余空间；
3. 依赖 Word 的段落和表格规则自动分页。

因此，单项点的最终高度取决于照片方向和页尾剩余空间，而不是由报告视觉规范决定。`fitPhotoTableToHeight()` 还会整体缩小照片，但不会同步改变表格单元格宽度，容易出现“单元格很大、照片很小”的观感。

另外，当前 `cantSplit` 只约束照片表格中的单行，不能保证一个包含两行照片的四图表格整体不跨页；`keepNext` 也主要绑定项点文字和照片表格的开头，不能把整个项点当成一个分页单元。

## 3. 方案选择

### 方案 A：项点整体分页 + 固定画幅网格（采用）

每个有照片的检查项点作为一个不可拆分的内容块，包含项点文字和照片网格。照片尺寸由照片数量和网格规则决定，不再由原始横竖比例或页尾剩余高度决定。页尾放不下完整项点时，整个项点从下一页开始。

优点是分页可预测、照片大小统一、Word 和 LibreOffice 的渲染差异较小，能够直接解决三张问题截图中的主要问题。

### 方案 B：所有照片统一固定 3:4 画幅

实现简单，分页稳定，但横屏照片会显得过高，单图和双图的视觉比例不够自然。3:4 也不是用户已经确认的最终画幅比例，因此不作为本次默认方案。

### 方案 C：保留原图比例的瀑布流布局

可以减少照片裁剪和拉伸，但 Word 表格的跨页、行高和空白控制复杂，混合横竖照片时仍然会出现视觉重心不齐，不适合作为本项目的长期排版基础。

## 4. 采用方案的视觉规则

### 4.1 项点布局

每个检查项点按以下顺序生成：

```text
项点文字
照片网格
项点间距
```

照片数量为 1—4 张时，项点文字与照片网格作为一个整体处理。当前页剩余空间不足时，项点文字和照片一起换页，禁止出现项点文字留在上一页、照片出现在下一页的情况。

对照片数量超过 4 张的极端情况，允许在照片行边界继续到下一页，但必须保证项点文字与第一行照片绑定；后续照片只能在完整行边界分页，不能拆开一行。

### 4.2 照片网格

照片网格最多使用两列，以避免三列布局导致照片过小：

- 1 张：单列、中等宽度、居中；
- 2 张：两列等宽、等高；
- 3 张：第一行两列，第二行单张居中；
- 4 张：两列两行，四张等宽、等高；
- 5 张及以上：继续使用两列等宽分行。

每个照片位置使用统一横向画幅。横屏和竖屏原图都允许在导出的 DOCX 显示副本中进行水平或垂直拉伸，以完整填充画幅；不裁剪、不留白。原始照片、IndexedDB 数据、Android 相册备份和预览图均保持不变。

单图不再默认铺满整个内容宽度，也不使用页尾剩余空间临时缩放。双图和四图不再按原始方向分别计算高度，因此同一网格中的照片保持统一视觉尺寸。

第一版实现使用可集中调整的横向画幅常量，初始尺寸建议如下：

- 单图约 150mm × 100mm，居中；
- 双图及四图中的单张照片约 78mm × 58mm；
- 列间和行间保留约 4mm 间距；
- 项点文字与照片网格之间保留约 3—5mm 间距。

这些数值是实现起点，不把 4:3 作为已经确认的业务要求。最终尺寸以 LibreOffice/Word 实际渲染后的视觉效果为准，并集中修改常量，不再新增用户设置。

## 5. 分页架构

### 5.1 内容块结构

有照片的项点使用一个无边框的外层表格块：

- 外层表格只有一个单元格和一个不可拆分行；
- 单元格内依次放置项点段落和照片网格；
- 照片网格内部的每一行仍设置 `cantSplit`；
- 不再依赖一串跨多个兄弟节点的 `keepNext` 来表达项点绑定关系。

无照片的项点继续使用普通段落，不插入空照片表格，也不把它与后续项点错误绑定。

### 5.2 页面估算

生成 DOCX 子节点时，分页估算器同时计算：

- 页面可用高度；
- 标题、正文和项点文字的预计行高；
- 当前照片网格的固定行高；
- 外层项点块的间距和安全余量。

如果完整项点块能放入当前页，则直接放置；如果不能放入但项点块小于一整页，则在项点块前插入明确的分页标记。分页估算必须使用与实际 `ImageRun` 相同的宽高数据，避免估算值与 Word 实际高度不一致。

不再执行“根据当前页剩余空间压缩照片”的逻辑。这样会保留部分有意留白，但留白只出现在完整项点无法放入时，不会出现照片被压小或项点被拆开的不确定结果。

### 5.3 章节标题

章节标题与该章节的第一个有照片项点共同参与分页判断。如果标题和第一个项点不能形成完整的可读块，则章节标题与项点一起从下一页开始，避免标题孤零零出现在页尾。

## 6. 代码边界

主要修改 `app/src/features/reports/generateDocx.ts`：


- 将照片网格布局计算与 DOCX 表格生成保持为同一份内部布局模型；
- 新增项点内容块的构造函数；
- 将分页估算从“单独估算文字和照片表格”调整为“估算完整项点块”；
- 删除或停用按剩余页面高度缩放照片的路径；
- 保留现有照片注释渲染、DOCX 专用压缩、媒体关系替换和错误检查流程。

主要修改 `app/src/features/reports/generateDocx.test.ts`：

- 增加单图、双图、三图、四图的统一画幅断言；
- 增加混合横竖照片的等宽等高断言；
- 增加项点文字和照片整体分页断言；
- 增加四图表格不得跨页拆行的结构断言；
- 增加页尾放不下时不缩小照片、整体换页的断言；
- 保留现有照片关系、压缩、无照片项点和固定模式测试。

不增加新的用户界面选项，不删除现有“照片排版模式”和“每行照片数”设置。推荐方案只作为当前自适应导出模式的内部实现；固定模式的兼容行为保留，待真实渲染验证后再决定是否统一其默认画幅规则。

## 7. 错误处理与数据保护

- 缺少已引用照片时继续抛出当前的报告生成错误；
- 布局尺寸统一限制为正整数，避免生成非法 DOCX 尺寸；
- 对超长项点或超过单页高度的照片组，按完整照片行继续分页，不生成负尺寸或无限缩放；
- 不修改原始照片 Blob、拍照记录、图库备份和报告数据；
- 任一照片布局失败都必须明确失败，不能静默丢失照片。

## 8. 验证标准

代码验证顺序：

1. 先运行新增的报告布局聚焦测试，并确认旧的失败用例能够复现当前问题；
2. 完成实现后运行 `pnpm exec vitest run src/features/reports/generateDocx.test.ts`；
3. 运行全量 `pnpm exec vitest run --maxWorkers=1`；
4. 运行 `pnpm run lint` 和 `pnpm run build`；
5. 使用真实横屏、竖屏照片生成 DOCX；
6. 使用 `C:\Program Files\LibreOffice\program\soffice.exe` 转 PDF 或渲染页面，逐页检查单图、双图、四图、跨页和章节首项点；
7. 只有在真实渲染通过后，才递增 Android 版本并生成新的 APK。

验收重点：

- 不出现项点文字与照片分离；
- 不出现同一四图项点上下两行跨页；
- 同一网格照片显示尺寸一致；
- 单图不再过大，双图和四图不再过小；
- 页面留白是完整项点换页产生的可解释留白，不是 Word 自动拆表或图片缩放造成的异常空白；
- 所有照片仍然出现在报告中，原始照片保持不变。

## 9. 非目标

- 不改变检查项点、排序、分类和报告文字；
- 不新增或删除业务功能；
- 不新增云端、账号或协作能力；
- 不把原始照片永久压缩或拉伸；
- 不在没有真实 Word/LibreOffice 渲染证据时宣称版面已经完成。
